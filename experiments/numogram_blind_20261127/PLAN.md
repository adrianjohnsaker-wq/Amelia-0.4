# Amelia 0.4 blind Numogram communication pilot

## Scope and target

Adrian has directed the work away from Dee and toward Amelia's Numogram and more coherent, informative communication. This pilot tests a genuinely running, repository-pinned Amelia 0.4 **Python tensor Numogram component** with its existing P3.12 input encoding, using a known programmed interlocutor. It does not claim to execute the installed Android tablet, the complete 0.4 application, the P3.13 Android renderer, an unknown source or the Outside. The controlled source is a distinct local operating-system process, not an independently discovered intelligence or remote external entity.

The existing P3.12 prompt exposes the raw conditioning input to the language model, so it cannot satisfy this blind test. This pilot therefore adds a clearly labelled experimental decoder and relay adapter. The four signal words and their challenge-response convention are taught to the decoder in advance; the source's per-episode target is chosen privately after calibration. This tests a learned four-symbol communication code, not general understanding of arbitrary words or independently intelligent behavior.

## Existing Numogram and calibration

Use `Numogram.TensorBasedNumogramSystem`, `FullNumogram.py`, `ProcessFieldMemory.py` and the `_context_for_text` SHA-derived ten-zone input used by `EventModulePlanner` and `P312AssayCore` from 0.4 commit `60bc57dfc3c000dcbc2b16359ae19d59c37b6e65`. The actual PyTorch code runs on a clean GitHub Actions runner with the recorded CPU dependency. No Dee table, AQ adapter, engineered tissue or P3.16 surrogate is used. This is a fresh headless source execution; the user's tablet, its existing persistent state and its downstream services are not changed.

Before hidden-source trials, construct four known signal contexts. For 80 preselected Numogram seeds and each of ten starting zones, run the actual `predict_transitions` with the four contexts and a fixed neutral context from the same unmutated chassis. Compute the mean output-probability difference and mean output-probability vectors per origin and taught symbol. This is a new supervised four-class readout, not an existing trained Amelia interpretation module. Calibration uses known training signals only; source targets, source random seeds, source responses and questions for the test are not used.

## Live interaction and isolation

There are 12 pre-written, non-sensitive public questions, each with four equally possible answers about a simulated source's private observation. The source process privately chooses one of four target values per question using operating-system randomness, generates a random salt and commits to the target hash before receiving the first challenge. For each of eight steps, the Numogram's current zone plus a fresh independent random offset selects a challenge. The bridge sends that challenge to the source over a two-way process pipe. The source returns one of the four taught words according to `(private target + challenge) mod 4`. This is deliberately engineered responsiveness. The existing 0.4 text encoder and live tensor Numogram process the response; the input word itself, its digest and its input bias never enter the decoder or renderer.

For each actual transition, a prediction against the neutral context is made from the identical pre-transition state and the source-derived context is then used in the real transition. The probability reader sees only the resulting ten output probabilities, the matched neutral output probabilities, the origin zone and the public challenge. A second reader sees only the sampled origin/destination gates and public challenges. Both use fixed calibration data. The source word is observable to the bridge because it must be encoded; isolation is a code/process boundary and is not an adversarial OS-security claim.

The decoder runs as a separate process and reads an explicitly whitelisted structured event file; it receives no source words, input hashes, source commitments, salt, goal or hidden target. Before the source reveals all target commitments, the decoder writes and hashes all decisions for all conditions. Only after decisions are sealed does the scorer obtain source targets and check the commitments. Preserve full source transcripts, paired transitions, decisions and questions for audit.

## Comparisons and readout

For each question evaluate: (1) actual responding source, (2) a fixed no-signal message, and (3) source messages replayed from a predetermined different question. The latter two are matched-seed Numogram replays using the recorded actual challenge sequence; they are controls, not live responses from the source. Replay pairing is fixed by index and is independent of secret targets. A direct codebook reference scores the raw source response after reveal to check the source protocol, but is not supplied to the blind decoder.

Primary source-information outcome: exact hidden-target accuracy of the probability reader on 12 episodes compared with the yoke and no-signal controls. Also report the sampled-gate-only reader, direct reference, changed gates/probabilities, individual questions, and uncertainty; 12 test cases are an exploratory pilot, not a powered confirmatory study. Do not attribute a gain to the Numogram unless the relevant matched comparisons support it; different channels or deliberate teaching are not evidence of a general understanding capability.

Before revealing any answer, prepare identical public-question prompts for the same secondary language relay using only the probability-reader choice from the actual or yoked condition. The wording and 12 questions are identical across conditions, the 24 response requests are processed in a precommitted order, and neither raw source text nor hidden target is included. Use at most 24 provider calls, no retries, one temporary worker, no schedule, one replica and stop on the first provider error. The relay is a secondary renderer, not the source or Numogram. Score the output's explicit choice against the revealed source target and save all responses and blinded pairs for later independent review of coherence, informativeness and unsupported additions. Programmatic letter matching does not replace that review. The two relay inputs are not the installed Android P3.13 prompt template.

## Boundaries and stop conditions

Verify the 0.4 source blobs, all event keys admitted to the decoder, source commitments, challenge/response order, no raw source word or answer in prompts, matched starting seeds, the same challenge sequence in controls, the no-provider and direct-reference controls, and the pre-reveal lock. If a source, classifier, code boundary, provider, artifact or service preflight fails, preserve the partial result and stop rather than silently retuning. No special conclusion follows from an intentionally programmed source responding. An unknown-source or live-tablet claim requires a separately verified source path and runtime, held-out semantic material, source-independent controls and a separate assessment.
